# AI 无限流游戏 · 方案 v1

> 状态：草案，待决策
> 定性：多人自主抉择 + AI 世界模拟 + 经济元进度的 PvPvE 副本制游戏
> 技术底座建议：Spring Boot + MySQL + Redis + WebSocket（贴合现有栈）

---

## 0. 一句话结论

方向成立，形态必须改：**AI 负责“世界看起来像真的”，确定性引擎负责“世界到底怎么算”**。判定交给 LLM 是项目最致命的设计错误；AI 生成的物品直接进经济系统是第二致命的。

---

## 1. 五个硬约束（先看这个，它决定架构）

### 约束一：判定不能交给 AI（PvP 场景下不可接受）

**依据**：AI 游戏主持人领域唯一公开的量化结论是，把判定拆成「骰子函数 + 状态函数」后，一致性显著优于纯生成式裁定
（[You Have Thirteen Hours... Enhancing AI Game Masters with Function Calling, arXiv 2409.06949](https://arxiv.org/abs/2409.06949)）。

**为什么在你这儿更致命**：单机 AI 游戏里 AI 偏心只是“体验不好”；你的游戏是玩家之间**合作或勾心斗角**，AI 一旦判了“你这个动作失败”，对手立刻获益。玩家会得出“AI 在帮对面”的结论，而这是**无法自证清白**的——LLM 输出不可复现、不可审计。

**结论**：
- 随机数：确定性可复现（`HMAC(seed, runId, turn, actorId)`）
- 判定：规则引擎纯代码
- AI：只做「自然语言 → 结构化意图」和「结构化结果 → 自然语言」

### 约束二：生成式内容 + 经济系统 = 无限刷取漏洞

你的设计里，失败损失带入物资与资金、带出的物资可交易、物资决定升级方向——这意味着物资有**真实经济价值**。而 LLM 生成物品是无上限的。

**结论**：
- 物品只来自策划预设的 `itemPool` 白名单 + 胜利结算表，AI **只能选，不能造**
- 结算层硬校验：`itemId ∉ (itemPool ∪ settleTable)` 直接拒绝并告警
- AI 自由描述的“看起来像道具”的东西，只进叙事文本，不进背包

> 这条不守住，玩家会用一句话刷出无限物资，三天内经济崩塌，且你事后无法追溯。

### 约束三：多人隐藏信息必须做隔离

每个玩家有隐藏手牌/隐藏身份/隐藏目标。**LLM 只要“知道”就会“说”**——这是模型固有倾向，不是提示词能根治的。

单机 AI Dungeon 不需要解决这个问题（[其官方 FAQ 至今仍有 “Why does the AI forget or mix things up?”](https://help.aidungeon.com/faq/why-does-the-ai-forget-or-mix-things-up)），多人必须解决。

**结论**：每个玩家一条独立 context，只拼装“该玩家视角可见”的切片。禁止把全局 RunState 整份喂给任何 LLM。做法见 §4。

### 约束四：成本与延迟

一局 4 人 × 15 回合 = 60 次玩家行动，每次至少 2 次 LLM 调用（意图解析 + 叙事渲染）。

| 假设：输入 3.5K / 输出 0.2K 每次 | 一局 token 量 | 单局成本量级 |
|---|---|---|
| 中低价模型（输入 ¥1~2/M，输出 ¥8/M） | ~210K 输入 / ~18K 输出 | ¥0.2 ~ 0.5 |
| 旗舰模型（输入 ¥10~30/M，输出 ¥30~100/M） | 同上 | ¥2 ~ 6 |

> 价格为量级估算，以你实际计费为准。结论：**免费玩家会烧钱**，必须做 token 预算 + 上下文组装，不能全量喂历史。

### 约束五：AI 的默认输出是“平庸且安全”的

无限流的爽点是规则怪谈 + 反转 + 打脸。LLM 默认倾向给出正确、安全、无聊的答案——这正是 Hidden Door 要自训 LoRA 的原因
（[Hidden Door: The right tool for the job](https://www.hiddendoor.co/blog/lora-low-rank-adaptation-narrative-game-dev-storytelling)，其整体架构是 [agentic story harness](https://www.hiddendoor.co/blog/agentic-story-harness-narrative-ai-context-model) 的多模型编排，而非单模型包打天下）。

**结论**：世界规则必须是**人工设计的高质量种子**，AI 在骨架上长肉。不要指望 AI 从零生成好玩且严密的副本。

## 2. 分层架构

```
┌─────────────────────────────────────────────────┐
│ L3 元层：账号 / 仓库 / 交易市场 / 段位 / 天赋树   │  MySQL + 流水
├─────────────────────────────────────────────────┤
│ L2 AI 叙事层：Narrator / NPC 扮演 / 意图解析      │  LLM（按玩家隔离上下文）
├─────────────────────────────────────────────────┤
│ L1 规则引擎层：判定 / 状态机 / 结算 / 可见性分发  │  纯代码，零 LLM
├─────────────────────────────────────────────────┤
│ L0 世界种子层：副本定义 / 规则集 / 物品池 / 结算表 │  人工编写 → YAML → DB
└─────────────────────────────────────────────────┘
```

**核心原则：L1 是唯一真相源（Single Source of Truth）。L2 是可丢弃的渲染层。**
LLM 挂了、超时了、返回垃圾了，游戏必须能继续跑（降级为纯文本事件提示）。

### 各层职责边界

| 层 | 能做 | 绝对不能做 |
|---|---|---|
| L0 | 定义世界、规则、物品池、胜负条件 | 运行时被修改 |
| L1 | 判定、改状态、结算、决定谁看到什么 | 调用 LLM 做判定 |
| L2 | 描述发生了什么、扮演 NPC | 改状态、发物品、定胜负 |
| L3 | 账号数据、经济守恒、元进度 | 感知局内未结算状态 |

## 3. 一回合完整数据流

```
玩家自由输入："我把手电筒扔向那个影子然后往左跑"

  ① [意图解析] ── LLM, JSON Schema 约束
     输出：{action:"throw", item:"torch", target:"shadow", move:"left"}
     ↑ 必须用 function calling / 强 schema，产出后由代码校验；
       解析失败 → 追问玩家，绝不让幻觉穿透到 L1

  ② [校验] ── 纯代码
     物品存在？在玩家背包？目标可见？动作在当前场景合法？
     不合法 → 返回结构化拒绝原因（不消耗回合）

  ③ [判定] ── 纯代码
     roll = HMAC(seed, runId, turn, actorId, actionType) → 17
     DC  = script.dc["throw_at_shadow"] → 15
     modifier 来源逐条列出 → 合计 +1（天赋）
     17 + 1 >= 15 → 成功

  ④ [状态变更] ── 纯代码，写 RunState
     items.torch -= 1；pos = "B"；events += combat_result

  ⑤ [可见性分发] ── 纯代码
     计算哪些事件对哪些玩家可见（B 区的人看到，A 区的人只听见声音）

  ⑥ [叙事渲染] ── LLM，按玩家隔离
     输入：仅该玩家可见的事件 + 该玩家视角的世界摘要（≤800 token）
     输出：2~3 句沉浸式描述

  ⑦ [广播] ── WebSocket 按人分发
```

**LLM 只出现在 ① 和 ⑥，且两处都可校验、可降级、可缓存。**

## 4. 核心数据结构

### Script（副本定义，L0）

```json
{
  "scriptId": "ln-001",
  "name": "第七号病房",
  "minPlayers": 3,
  "maxPlayers": 6,
  "rules": [
    {
      "id": "r1",
      "text": "凌晨三点后，不得回应任何人叫你的名字",
      "detect": {"event": "respond_to_name", "timeEnv": ">=03:00"},
      "penalty": {"san": -1}
    }
  ],
  "winCondition": {"op": "all", "conds": [{"type": "reach", "id": "exit"}]},
  "failCondition": {"op": "any", "conds": [{"type": "all_dead"}]},
  "hiddenReward": {
    "trigger": {"and": [
      {"flag": "saw_ghost"},
      {"eq": {"stat": "san_min", "value": 2}},
      {"not": {"flag": "used_scalpel_on_npc"}}
    ]},
    "rewardItems": ["ward_key"]
  },
  "itemPool": ["torch", "scalpel", "gauze", "ward_key"],
  "dcTable": {"throw_at_shadow": 15, "pick_lock": 12},
  "settleTable": {
    "win":  {"items": {"gauze": 2}, "gold": 120},
    "lose": {"items": {}, "gold": 0}
  }
}
```

> `hiddenReward.trigger` 必须是**可判定的表达式**，不是自然语言。这是 AI 生成剧本能否落地的前提。

### RunState（一局状态，L1 唯一真相源）

```json
{
  "runId": "r_20260423_001",
  "scriptId": "ln-001",
  "seed": "hmac-derived-secret",
  "turn": 7,
  "phase": "night",
  "players": [
    {
      "uid": "u1",
      "hp": 2, "san": 3,
      "pos": "B",
      "items": {"scalpel": 1, "torch": 0},
      "broughtIn": {"knife": 1},
      "flags": ["saw_ghost"],
      "alive": true
    }
  ],
  "world": {"lights": "off", "ward6_door": "locked"},
  "log": []
}
```

**持久化策略**：
- Redis 存热状态（当前局的 RunState），带 TTL
- MySQL 存 `run` 主表 + `run_event` append-only 事件流（可回放、可审计、可做反作弊取证）
- `log` 是 append-only 的，任何状态变更必须先落事件再改快照 → 保证任何一局都能完整重放

## 5. 判定：可审计随机

```
roll = HMAC_SHA256(seed, f"{runId}:{turn}:{actorId}:{actionType}") % 20 + 1
```

- `seed` 开局生成，存在 MySQL 不向玩家暴露
- **可复现**：同样的 runId/turn/actor/action 永远得到同样的骰子 → 玩家争议时可回放验证
- **不可预测**：玩家无法从外部推算（seed 保密）
- **不可被 AI 影响**：L2 拿不到 seed

**判定透明化（PvP 信任的生命线）**：
每次判定必须向玩家摊开三行：

```
掷骰 17   DC 15   加值 +1（天赋：夜行者）
→ 成功
```

玩家可以不接受“运气”，但必须能接受“明账”。**不做这个，玩家会默认 AI 在偏袒对手。**

## 6. 信息隔离

每个玩家一条 `VisibilitySlice`：

```java
// 伪代码
Slice buildSlice(RunState s, String uid, Event e) {
    return Slice.builder()
        .selfState(s.player(uid).publicView())         // 自己的完整状态
        .othersPublic(s.others(uid).map(Player::publicView)) // 别人只有公开字段
        .visibleEvents(e.filterSeenBy(uid))             // 只含该玩家能感知的事件
        .scenePublic(s.world().publicView())            // 世界公开部分
        .build();
}
```

**铁律**：
1. 拼装 context 的函数**只接受 `uid`**，不接受 `RunState` 全量 —— 从签名上堵死泄密路径
2. 隐藏字段（`flags`、`broughtIn`、其他玩家的 `items`）在 `publicView()` 里根本不存在，不是靠提示词“不要说出来”
3. 上线前必须做**泄密红队测试**：让玩家用 20 种方式诱导 AI 说出他人隐藏信息，0 次成功才算过

## 7. 经济守恒（最容易被忽略，出事最严重）

### 物资生命周期

```
账号仓库 ──带入──> 局内背包 ──┬──胜利结算──> 账号仓库（记为产出）
                            └──失败/死亡──> 销毁（记为销毁，不是"损失"）
局内产出：只能来自 settleTable / hiddenReward.rewardItems（白名单内）
```

### 对账公式（每局结束必须跑，误差必须为 0）

```
Σ带入 + Σ局内产出(结算表内) == Σ带回 + Σ销毁 + Σ局内消耗 + Σ遗失
```

### 记账方式

- **双边流水**：任何余额变动生成两条记录（出/入）+ 一条手续费进 sink 账户
- 所有物品实例带 `origin_run_id`，可追溯到哪一局产出
- **反刷**：
  - 同一 `origin_run_id` 的产出总量 ≤ 结算表上限
  - 交易有最小单位与频率限制
  - 单日单账号产出熔断阈值

### 交易市场

- 平台抽成（sink，不回流）——这是唯一能对抗通胀的手段
- 没有 sink 的虚拟经济必然通胀。**必须设计“钱和物资的消耗出口”**，否则玩家囤积 → 物价崩 → 元进度失去意义

## 8. 天赋平衡约束

你的直觉是对的（“不会有绝对影响战局”），把它变成可执行的规则：

| 规则 | 说明 |
|---|---|
| 只能是 modifier，不能是 enabler | “判定 +1”可以；“能穿墙”不行 |
| 每条天赋带 powerBudget（1~3） | 每阶一个，累计上限受阶数约束 |
| **主线判定禁用天赋加成** | 规则引擎按 `context` 分类：`context == "climax"` 时忽略所有天赋 modifier |
| 天赋只影响“边缘判定” | 开门、攀爬、潜行可以；胜负条件、隐藏奖励触发条件不行 |

实现上：结算与胜负判定走 `strictModifierSet()`（空集），只有普通行动判定走 `fullModifierSet(uid)`。

## 9. 分期路线（每期都有明确 gate）

### M0 · 1~2 周 · 单副本离线验证“好不好玩”
- 范围：1 个副本、单人、规则引擎 + 1 个 LLM 叙事者，本地跑
- **不做**：多人、经济、交易、元进度
- **Gate**：你自己连玩 3 遍，想再来一次。
- **这一关不过，后面全部不用做。** 这是整个项目唯一真正的风险点：AI 造的副本到底好不好玩。

### M1 · 2~3 周 · 多人同房 + 信息隔离
- WebSocket 同步、按人独立 context
- **Gate**：泄密红队测试 20 次，0 次泄露；4 人同房无状态错乱

### M2 · 2~3 周 · 经济闭环
- 带入/销毁/产出/交易/抽成
- **Gate**：每局自动对账，`Σ带入 == Σ带回 + Σ销毁 + Σ消耗`，误差 0；模拟 100 局无异常

### M3 · 1~2 周 · 元进度 + 天赋
- **Gate**：注入全天赋的账号打主线，胜负条件判定结果与无天赋账号完全一致

### M4 · 动态副本（AI 生成剧本）
- **放到最后**。前四期已经是一个完整产品了。
- 风险最高、收益最不确定。前提：`hiddenReward.trigger` 这类结构必须先做到“可判定表达式”，AI 生成才有落点。

## 10. 风险清单

| 风险 | 严重度 | 缓解 |
|---|---|---|
| AI 判定偏心 → PvP 信任崩塌 | 致命 | 判定全在代码 + 摊开明账 |
| 生成物品刷取 → 经济崩 | 致命 | itemPool 白名单硬校验 |
| 隐藏信息泄露 | 高 | 签名级隔离 + 红队测试 |
| AI 生成的副本不好玩 | 高 | M0 先验证；规则种子人工化 |
| 玩 10 局后摸清 AI 行为模式，新鲜感断崖 | 中高 | 人工种子库 + 随机组合 |
| 免费玩家烧钱 | 中 | token 预算 + 上下文压缩 + 降级小模型 |
| 虚拟经济通胀 | 中 | 交易抽成 sink + 消耗出口 |
| 资金可充值可提现 → 涉监管 | 高 | 见 §11 决策二 |

## 11. 需要你拍板的三件事

### 决策一：实时 vs 异步（决定整个技术栈）
- **实时同房**（像 Among Us）：体验强，但 LLM 每次响应 2~5 秒会打断节奏，需做“假即时”（先播占位动画）
- **异步回合**（像文字团，每人每天若干次行动）：对延迟宽容、成本可控、能做深度剧情，但爽点密度低

### 决策二：资金与物资是否可变现（决定合规成本）
- **纯虚拟不可提现**：自由度高，风控压力小
- **可充值 / 可提现**：这就是金融系统，需要反洗钱、风控、可能涉及监管。你原话里的“损失一部分资金”如果是真钱，架构和合规成本要另算

### 决策三：副本人工设计 vs AI 生成
- 你的原设想是“场景由 AI 决定”
- 但爽点来自“规则严密到能整人”的怪谈设计，这个 AI 目前做不好
- 建议：**M0~M3 全部人工设计副本，M4 再引入 AI 生成**，且 AI 生成的是骨架上填的肉

## 12. 与你的原设想对照

| 你的原设想 | 本方案 | 改动理由 |
|---|---|---|
| 剧情由 AI 决定 | 骨架人工，AI 填肉 | AI 造不出严密规则 |
| 判定由 AI 决定 | 判定纯代码，AI 只渲染 | PvP 下不可审计、不可信 |
| 失败损失物资与资金 | 保留，但改为“销毁”+逐笔审计 | 可追溯、可反作弊 |
| 物资互相交易 | 保留，加抽成 sink + 反刷 | 无 sink 必通胀 |
| 每阶一个小天赋 | 保留，加 modifier/enabler 边界 + 主线禁用 | 保证“不影响战局”可执行 |
| 完全自主抉择 | 保留（自然语言自由输入） | 这是本方案唯一 100% 保留的核心体验 |
